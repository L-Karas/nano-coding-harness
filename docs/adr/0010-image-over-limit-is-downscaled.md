# 超过上限的图片等比缩小，而不是拒绝

## Status

accepted

`core/tools/vision.py` 的 `MAX_IMAGE_BYTES`（5 MB）仍是唯一上限，但超限不再是终点：`fit_image()`
先判上限，超限的交 `shrink_image()` 用 Pillow 按「字节数 ∝ 像素数」估一个初始比例，等比缩小后重编码
（保留原格式，JPEG / WebP 按 85 质量输出），循环收紧到编码结果落在上限内。本地图片（`read_file`）
与 MCP 返回的 `ImageContent` 走同一条规则；正文注明 `downscaled from <size>`，MCP 结果追加一行
缩小说明，模型因此知道看到的是缩略版而不是原图。

只有缩不下来的才回到 `Image too large` 错误：Pillow 解不开的字节、多帧动图（缩放会丢帧，宁可
报错也不静默丢动画）、以及缩到 1x1 仍超限。重编码的 MIME 以 Pillow 识别出的真实格式为准，后缀
与外部来源自报的 MIME 只用于早期判类型；EXIF 方向在重编码前烧进像素，避免缩小后的手机照片
躺倒。异步路径的缩小 / 重编码经 `asyncio.to_thread` 让出 loop，同步路径直接算。

## Considered Options

- **等比缩小 + 保留原格式**（采纳）：视觉模型仍拿到完整画面；同一张图换个尺寸就够，不必改格式
  或把质量压到底。
- **维持拒绝**（拒绝）：5 MB 以上的截图 / 照片很常见，让模型改用别的工具反而更贵，也拿不到图。
- **一律转 JPEG 压质量**（拒绝）：透明 PNG 与截图会丢 alpha 与线条锐度，且编码格式与后缀 / 自报
  MIME 不一致时更难解释。
- **动图逐帧缩小**（拒绝）：帧时长、调色板与循环语义都要自己搬，收益只覆盖极少见的超大 GIF。
